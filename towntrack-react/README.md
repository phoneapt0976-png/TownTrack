# TownTrack — React interactive prototype

React + Tailwind CSS + Lucide React สำหรับสาธิตระบบดูแลปัญหาชุมชนครบ 5 บทบาท แยก URL การทำงานตามบทบาท ใช้หน้าจอโทนสีขาวและฟ้า อ่านง่ายบนมือถือและจอใหญ่ รองรับเว็บ/PWA และแอป Capacitor สำหรับ iOS/Android

## เริ่มพัฒนา

ใช้ Node.js ตามที่ Vite รองรับ (20.19+ หรือ 22.12+)

```sh
npm --prefix ./towntrack-react ci
npm run dev -- --port 8770
```

ถ้าพอร์ตที่ระบุถูกใช้งานอยู่ เซิร์ฟเวอร์จะลองพอร์ตถัดไปอัตโนมัติ และแสดง URL ที่ใช้จริงใน Terminal

เปิด `http://localhost:8770/` เพื่อเลือกบทบาท หรือเปิดหน้าแต่ละบทบาทโดยตรง:

- `/citizen` — ประชาชน
- `/staff` — เจ้าหน้าที่รับเรื่อง
- `/supervisor` — หัวหน้าผู้ลงพื้นที่
- `/worker` — ผู้ลงพื้นที่
- `/authority` — ผู้มีอำนาจ / ผู้บริหาร

แต่ละ URL เป็นพื้นที่ทำงานแยกกัน ไม่มีแถบสลับบทบาทด้านบน หน้าเว็บโหลดคำร้อง 50 รายการล่าสุดจาก Neon และคำร้องใหม่บันทึกกลับไปยัง Neon ส่วนบัญชีทดลองทีม A/B เลือกได้จากหน้า desktop ของบทบาทที่เกี่ยวข้อง

```sh
npm test
# เปิด dev server ที่ port 8770 ก่อนรันการทดสอบเบราว์เซอร์
npm run test:e2e
npm run build
npm run preview -- --port 8771
```

## นำเข้าข้อมูลสาธิตไป Neon (development)

คัดลอก `.env.example` เป็น `.env.local` แล้วใส่ connection string ของ Neon development ใน `DATABASE_URL` (อย่าใช้ URL ที่มีสิทธิ์ production หรือเผยแพร่ URL นี้เป็นตัวแปร `VITE_`) จากนั้นรันจากโฟลเดอร์โปรเจกต์หรือ workspace root:

```sh
npm run db:seed:demo
```

สคริปต์เพิ่มข้อมูลสาธิต 50 รายการลงตาราง `reports` โดยใช้คอลัมน์ `title`, `description`, `location` และ `citizen_id` หัวข้อจะขึ้นต้น `[ข้อมูลจำลอง]` และ `citizen_id` จะขึ้นต้น `towntrack-mock:` เพื่อแยกจากคำร้องจริง การรันซ้ำจะข้ามรายการเดิม

ตั้งค่า `DATABASE_URL` ใน `.env.local` ก่อนเริ่มเว็บด้วย `npm run dev` หรือรัน production build ด้วย `npm run build` แล้วเปิดเซิร์ฟเวอร์ด้วย `npm start` (หรือ `npm run preview`) API ใช้ตาราง `reports` ที่มีคอลัมน์ `id`, `title`, `description`, `location`, `citizen_id` และ `created_at` หากนำไป deploy ต้อง deploy Node server นี้พร้อมกำหนด `DATABASE_URL` ใน environment ของ server

### Deploy บน Vercel

ตั้งค่า Root Directory ของ Vercel เป็น `towntrack-react` แล้วเพิ่ม Environment Variable ชื่อ `DATABASE_URL` ด้วย connection string ของ Neon ใน Vercel Project Settings → Environment Variables จากนั้น redeploy production deployment ล่าสุด ไฟล์ `api/reports.js` ให้ endpoint `/api/reports` สำหรับ Vercel โดยตรง

## เปิด build โดยไม่ติดตั้ง Node

ในโฟลเดอร์ `dist` รัน `python3 -m http.server 8766` แล้วเปิด `http://localhost:8766/` ต้องเปิดผ่าน HTTP เพื่อใช้ LocalStorage และ IndexedDB อย่างสม่ำเสมอ ไม่ลาก index.html เปิดแบบ file://

## OIDC, LINE OA และมือถือ

คัดลอก `.env.example` เป็น `.env.local` แล้วกำหนด issuer, client ID, callback และ role claim ให้ตรงกับ Identity Provider แอปใช้ Authorization Code + PKCE, ตรวจ ID token แบบ RS256 ผ่าน JWKS และตรวจ role claim ให้ตรงกับบทบาทที่เข้าใช้ โดยไม่ฝัง client secret

```sh
cp .env.example .env.local
# ตั้งค่า VITE_OIDC_ISSUER, VITE_OIDC_CLIENT_ID และ callback สำหรับเว็บ
npm run build
npm run cap:sync
npm run cap:open:ios
npm run cap:open:android
```

เว็บ/PWA ใช้ public SPA client และ HTTPS callback เช่น `https://your-domain.example/auth/callback` (localhost HTTP ใช้ได้เฉพาะพัฒนา) ส่วนแอปมือถือเปิดหน้าเข้าสู่ระบบใน browser ภายนอก แล้วรับ deep link กลับด้วย Capacitor App API ใช้ค่าเริ่มต้น `com.towntrack.app://auth/callback` สำหรับทั้ง iOS และ Android และสามารถตั้ง `VITE_OIDC_NATIVE_REDIRECT_URI` กับ `VITE_OIDC_NATIVE_CLIENT_ID` แยกจากเว็บได้ ระบบใช้ native HTTP bridge ของ Capacitor สำหรับ discovery, JWKS และ token endpoint บนมือถือ

ประชาชนเข้าผ่าน LINE OA ด้วย LIFF: กำหนด `VITE_LINE_LIFF_ID`, ตั้ง LIFF Endpoint URL ให้ชี้มาที่หน้า `/citizen` บน HTTPS และนำ LIFF URL ไปใส่ใน Rich Menu หรือข้อความต้อนรับของ OA หากต้องการปุ่มเปิดบัญชีทางการ ให้กำหนด `VITE_LINE_OA_URL` ด้วย LIFF URL รองรับการเปิดผ่าน LINE บน iOS/Android แต่อาจเปิดใน browser ภายนอกตามการตั้งค่าของระบบ จึงควรลอง Rich Menu บนอุปกรณ์จริงก่อนเผยแพร่ เมื่อยังไม่ตั้ง LIFF ID หน้า local demo จะยังเข้าโหมดตัวอย่างได้ บทบาทเจ้าหน้าที่ทั้งสี่ใช้ OIDC ตามเดิม

เพิ่ม callback URI ใน Identity Provider และตั้งชื่อ scheme ให้ตรงกับ `VITE_OIDC_NATIVE_REDIRECT_URI` หากเปลี่ยน `appId` หรือ scheme ต้องแก้ URL scheme ใน `ios/App/App/Info.plist` และ intent filter ใน `android/app/src/main/AndroidManifest.xml` ให้ตรงกันด้วย ค่า team/bundle signing ของ Apple และ Android SDK เป็นค่าของผู้เผยแพร่แอป ไม่ควรใส่ secret ลงใน `.env` ฝั่ง frontend

Capacitor รองรับ Android, iOS และเว็บ; การ build iOS ต้องใช้ macOS กับ Xcode ส่วน Android ต้องติดตั้ง Android Studio และ SDK ก่อนเปิด native project [ข้อกำหนดระบบของ Capacitor](https://capacitorjs.com/docs/getting-started/environment-setup) โค้ด OIDC ฝั่งแอปพร้อมใช้กับผู้ให้บริการที่อนุญาต public native client และ custom-scheme redirect แล้ว แต่ข้อมูลเรื่องและไฟล์ในต้นแบบยังอยู่ในเครื่อง ต้องเชื่อม API ฝั่ง server และตรวจสิทธิ์ทุก request ก่อนใช้ production

## สิ่งที่ทำงานแล้ว

- ข้อมูลตัวอย่าง 300 เคส; Top 5 เรียงยอดโหวต; แผนที่ OpenStreetMap ผ่าน Leaflet พร้อมหมุดและกลุ่มหมุด
- ตรวจระยะ Haversine 100 เมตร พบเคส 003/004; โหวต 1 ครั้งต่อตัวตนทดลอง; ติดตาม/ยกเลิกติดตาม; แยกเรื่องตนเองและเรื่องที่ติดตาม
- เมื่อเรื่องที่แจ้งเองหรือเรื่องที่ติดตามปิดแล้ว หน้าติดตามจะแสดงแบบประเมินความพึงพอใจ 1–5 คะแนนพร้อมความคิดเห็นเพิ่มเติม (ไม่บังคับ) ประเมินได้หนึ่งครั้งต่อคนต่อเรื่อง เจ้าหน้าที่เห็นผลประเมินในรายละเอียดเรื่อง ตัวอย่างทดลอง: เรื่อง TT-019 ในแท็บ “เรื่องที่ฉันแจ้งเอง” และ TT-005 ในแท็บ “เรื่องที่ติดตาม”
- ส่งคำร้อง บังคับรายละเอียดและรูป/วิดีโออย่างน้อย 1 ไฟล์ เบอร์ไม่บังคับ (ตรวจรูปแบบเมื่อกรอก) แนบได้สูงสุด 5 ไฟล์ต่อช่อง ขนาดน้อยกว่า 10 MB/ไฟล์
- เจ้าหน้าที่ขอข้อมูลเพิ่มได้จากคิวรับเรื่อง; ประชาชนแก้รายละเอียดและแนบหลักฐานเพิ่มได้ภายใน 7 วัน จากนั้นระบบปิดเรื่องเมื่อครบกำหนด และส่งกลับเข้าคิวเจ้าหน้าที่เมื่อตอบครบ
- โฟลว V.3 ไม่รับคำร้องไฟไหม้ ไม่มี popup หลังส่ง และไม่มีคิวฉุกเฉิน; คำร้องใช้ระดับทั่วไป/เร่งด่วน
- เทศบาลรับ/ปฏิเสธพร้อมเหตุผล ประเมิน ส่งหัวหน้าทีมหรือข้อเสนอ จัดการคำสั่ง และตรวจปิด/คืนแก้
- หัวหน้าทีมจัดผู้ลงพื้นที่ ประเมินทรัพยากร ส่งข้อเสนอ ตรวจคุณภาพจากภาพก่อน/หลัง แล้วส่งเทศบาล
- ผู้ลงพื้นที่รับ/ปฏิเสธพร้อมเหตุผล เริ่มงาน ขอทรัพยากร ส่งรายงานพร้อมภาพ/วิดีโอก่อนและหลัง
- ผู้มีอำนาจอนุมัติ/ไม่อนุมัติ/ขอข้อมูลเพิ่มข้อเสนองบและคำสั่ง พร้อมเหตุผลและเลขอ้างอิง และภาพรวมสถิติ
- แบบร่างข้อเสนอเก็บแยก ยังไม่เข้าคิวผู้มีอำนาจจนกดส่ง; ไฟล์แบบร่างที่ยังไม่ส่งต้องแนบใหม่หลังปิดหน้า
- เก็บประวัติข้อเสนอหลายฉบับ รายงานหลายรอบ และการตรวจ; งานปิดอ่านอย่างเดียว; ตรวจ revision ป้องกันทับข้อมูลเก่า
- การอนุมัติงบยังต้องให้เทศบาลบันทึกหลักฐานทรัพยากร/ขั้นตอนพร้อมก่อนส่งทีมเริ่มงาน
- React Context อัปเดตทุกบทบาททันที และ storage event สำหรับหลายแท็บของ origin เดียวกัน
- บันทึกไฟล์ใน IndexedDB แยกจาก LocalStorage พร้อม rollback ไฟล์ใหม่เมื่อคำร้องบันทึกไม่สำเร็จ

## โครงสร้าง

- `src/model.js`: ฐานข้อมูลตัวอย่าง ระยะตำแหน่ง และกฎเปลี่ยนสถานะ (ทดสอบแยกจาก UI)
- `src/store.jsx`: Context, LocalStorage, IndexedDB, การบันทึกและ toast
- `src/Citizen.jsx`: portal, 100m, form, tracking และเบอร์ช่วยเหลือ
- `src/line-liff.js`: ทางเข้า LIFF และยืนยันตัวตนประชาชนผ่าน LINE
- `src/Office.jsx`: หน้าบุคลากร 4 บทบาท dashboard, proposals, reports และ actions
- `src/components.jsx`: ปุ่ม badge modal แผนที่ timeline media uploader และข้อมูลร่วม
- `tests/model.test.mjs`: การทดสอบกติกาธุรกิจด้วย Node test runner
- `tests/e2e.cjs`: ทดสอบในเบราว์เซอร์ (ใช้ @playwright/test และ Google Chrome ที่ติดตั้งในเครื่อง)

## ขอบเขตที่ต้องทำก่อนใช้งานจริง

นี่เป็น prototype ที่ build สำหรับเผยแพร่ได้ ไม่ใช่ระบบราชการ production ที่พร้อมรับเหตุจริง

1. Role Switcher และบัญชีบุคลากรเป็นตัวตนจำลอง; LIFF ฝั่งหน้าเว็บใช้เพื่อสาธิตทางเข้าประชาชนเท่านั้น ต้องส่ง ID token ไปตรวจสอบกับ LINE และตรวจสิทธิ์บน backend ทุก request ก่อนใช้จริง
2. ไม่มี LINE push, SMS/OTP หรือแจ้งหน่วยฉุกเฉินจริง และ `02-123-4567` เป็นเบอร์ตัวอย่าง ต้องแทนด้วยเบอร์ที่เทศบาลยืนยันก่อนใช้จริง
3. แผนที่จริงจาก OpenStreetMap แต่ตำแหน่งของข้อมูลตัวอย่างเป็นพิกัดจำลอง ไม่ได้ตรวจเขตเทศบาลทางราชการ GPS จะขอสิทธิ์เมื่อกดปุ่ม ใช้ได้บน HTTPS/localhost และเลือกจุดบนแผนที่แทนได้
4. ข้อมูลและไฟล์อยู่ในเบราว์เซอร์ของเครื่องนั้น การปิดเรื่องเมื่อครบ 7 วันจะทำงานเมื่อแอปเปิดหรือกลับมาใช้งาน ต้องย้ายการตั้ง deadline และงานปิดอัตโนมัติไป backend scheduler เพื่อให้ทำงานได้แม้ผู้ใช้ปิดแอป และใช้ API/ฐานข้อมูล/object storage เมื่อใช้หลายเครื่อง พร้อมกำหนดนโยบายข้อมูลส่วนบุคคล/สำรอง/เก็บรักษา
5. การอนุมัติใน UI ไม่ใช่ลายมือชื่อทางราชการ ไม่ใช่การตรวจรับพัสดุ ต้องกำหนดคำสั่งมอบอำนาจ ลำดับอนุมัติ และเอกสารจริง
6. Prototype ใช้ key `towntrack-react-v1` และฐานไฟล์ `towntrack-media` ข้อมูลจากเว็บรุ่นก่อนเก็บไว้เดิม ไม่ถูกลบหรือย้ายเข้า schema ใหม่โดยอัตโนมัติ

เบอร์ดับเพลิงในตัวอย่าง 199 เป็นลิงก์เปิดแอปโทรศัพท์ ไม่มีการโทรหรือส่งเรื่องอัตโนมัติ

## หน้าจอแดชบอร์ดสาธารณะ

`src/PublicDashboard.jsx` ปรับโครงหน้าจอโดยอ้างอิง [Traffy Bangkok](https://bangkok.traffy.in.th/) ใช้ชื่อและข้อมูล TownTrack เอง ไม่มีการเชื่อมฐานข้อมูลของ Traffy แผนที่เป็น OpenStreetMap ภาพในเคสจำลองมาจาก Wikimedia Commons พร้อมแหล่งที่มาและสิทธิ์ใช้งานใน `public/sample-images/credits.html` ไม่ใช่ภาพเหตุการณ์จริงในเทศบาล

ค้นหาเลขเรื่อง/สถานที่ กรองประเภทหรือกดกล่องสถานะ โหวต ติดตาม เปิดรายละเอียด และดาวน์โหลด CSV ของรายการที่กรองได้ CSV ไม่มีชื่อผู้แจ้งหรือเบอร์โทร

ทดสอบหน้าจอเพิ่มเติมด้วย `node tests/dashboard.cjs`, `node tests/interaction-edges.cjs` และ `node tests/gps-evidence.cjs` เมื่อเปิด dev server แล้ว

เว็บจะเติมข้อมูลตัวอย่างให้ครบ 300 เรื่องครั้งเดียวเมื่ออัปเกรดฐานข้อมูลเดิม โดยรักษาคำร้องและการแก้ไขเดิมไว้ คำร้องใหม่แสดงหน้าแรกทันที เรียงวันที่ล่าสุด เปิดดูรายละเอียดและไฟล์แนบได้ โทรศัพท์และชื่อยังแสดงเฉพาะหน้าบุคลากร

## ข้อมูลบริการและมาตรฐานเว็บไซต์ภาครัฐ

เพิ่มศูนย์ข้อมูลที่ `/information?section=guide` (ภาษาอังกฤษเติม `&lang=en`), footer ทุกบทบาท, คู่มือ/FAQ, หน้าติดต่อและแผนผังเว็บ, หน้าคำอธิบายนโยบายต้นแบบ และเครื่องมือปรับการอ่าน อ่านขอบเขตที่ทำแล้วและงานของหน่วยงาน/Backend ที่ยังต้องดำเนินการใน [รายการเทียบมาตรฐาน DGA](docs/government-website-standard.md)

ตั้งข้อมูลสาธารณะของหน่วยงานและ URL นโยบายที่ได้รับอนุมัติด้วยตัวแปร `VITE_AGENCY_*` ใน `.env.example` ก่อน build หากยังไม่ตั้งค่าจะไม่แสดงเบอร์ อีเมล หรือข้อมูลหน่วยงานที่แต่งขึ้น เมนูหลัก ปุ่มทำงานหลัก สถานะ และคู่มือแยก 5 บทบาทเลือกไทย/อังกฤษได้จากแถบด้านบน โดยจำค่าภาษาในเบราว์เซอร์ ข้อมูลที่ประชาชนกรอกและข้อมูลตัวอย่างบางส่วนยังแสดงตามภาษาต้นฉบับ การปรับ Frontend นี้ยังไม่ใช่การรับรองว่าผ่านมาตรฐานหรือกฎหมายทั้งหมด

## โฟลว V.3 และ GPS

ไม่อนุญาต GPS ก็แจ้งและติดตามเรื่องได้โดยปักหมุดหรือกรอกพิกัดเอง ไม่มีการค้นหาหรือแสดงหน่วยช่วยเหลือใกล้ตัวจนกว่าจะได้รับสิทธิและพิกัดจริง เมื่อเพิกถอนสิทธิจะยกเลิกคำขอและซ่อนผลเดิม เบอร์ส่วนกลางยังใช้ได้

Dataset version 3 นำข้อมูลสาธิตไฟไหม้ออก คำร้องไฟไหม้ที่ผู้ใช้เคยสร้างเก็บสำรองใน `retiredIssues` และนำออกจากคิวทำงาน รายการอื่นที่เคยมี priority emergency เปลี่ยนเป็น urgent โดยคงประวัติเดิมไว้
